# Benchmarks: util-unix against GNU, 2026-11-07

Ratios are ours / GNU: below 1.00 means ours used less. They were produced by
`sh bench/run.sh` (see `bench/README.md` for the method) and are one run per
case, so treat small differences as noise.

## Setup

| | |
|---|---|
| Machine | AMD Ryzen 5 4600H, 12 threads, about 6 GB RAM, WSL2 (Linux 6.18.54.1-microsoft-standard-WSL2) |
| Scratch file system | tmpfs (`/tmp`) |
| Tool | poop, commit d683114 (`../poop`), `-d 1000` ms per command, standard input on /dev/null |
| Ours | util-unix at 7c673ff plus the new `bench/cases.txt` entries; `zig build -Doptimize=ReleaseFast`, stripped, Zig 0.17.1 |
| Reference | `/usr/bin/<util>`: GNU coreutils 9.7 (getent: glibc 2.43), dynamically linked |
| Locale | `LC_ALL=C` for both sides |
| Input | 100 directories of 100 empty files, owned by the current user, files 644, directories 755 |

## Reading the numbers

- **Start-up-dominated commands** (`id`, `groups`, `tty`, `uname`, `getent`
  lookups): ours used 0.08-0.23 of GNU's cycles and 0.11-0.37 of its
  instructions, and wall time ranged from 0.45 to 0.90. These commands do almost
  no work, so the difference is mostly process start-up. A static binary with
  no dynamic loader is a likely reason, but that was not isolated here.
- **Tree walks with chown and chgrp:** 0.43-0.54 of GNU's cycles, wall 0.71-0.91.
- **`chmod -R`: no meaningful difference.** Wall 0.93-1.01, cycles 0.82-0.90 and
  instructions 1.09-1.10. The work is one `chmod` call per file, and the kernel
  time dominates. Single-file chmod (0.77-0.84 wall) behaves like the other
  start-up-dominated cases.
- **Peak RSS** came out at 1.00-1.01 in every case, as in earlier runs of this
  harness. The cause was not investigated, so no memory claim is made.
- **Binary size is the cost:** the stripped ReleaseFast binaries are 4.4-7.7
  times larger than GNU's (about 245-306 KB against 35-68 KB), because each one
  carries Zig's `std.Io` runtime and statically linked code. GNU's figures
  exclude libc, which it loads from a shared library.

## Caveats

- One run per case, 1 second each, on WSL2 where wall time swings by up to 2x
  between runs; ratios within about 20% are noise (`bench/README.md`).
- The `chmod`, `chown` and `chgrp` tree cases change nothing (same owner, same
  mode), so they measure traversal plus a syscall per file, not real changes.
- `getent` reads the files only while glibc goes through NSS, so its ratios show
  that difference, not equal work (decision 0004).
- Nothing here says anything about correctness (see `test/`) or about other
  machines, file systems or kernels.
