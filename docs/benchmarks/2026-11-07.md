# Benchmark: split vs GNU coreutils 9.7 (2026-11-07)

Tool: [poop](https://github.com/andrewrk/poop) (`../poop/zig-out/bin/poop`), 1000 ms
per command, `sh bench/run.sh split`, ReleaseFast stripped build, Zig 0.17.1,
WSL2 on Linux 6.18, tmpfs `/tmp`, `LC_ALL=C`. Inputs: `text.txt` (300000 lines,
about 13 MB), `csv.txt`, `small.txt` (first 10000 lines of `text.txt`), generated by
`bench/gen.sh`. Ratios are ours / GNU (below 1.00 is better for us).

## Reading the numbers

- Wall time is within noise (about 20%, see `bench/README.md`) of GNU for every
  case. Peak RSS is equal.
- Fewer cycles and instructions than GNU for the byte-oriented and chunk modes
  (`-b`, `-n`, `-n l/N`, `-n r/N`, K/N extraction): positional reads and large
  writes.
- More instructions than GNU where work is per record or per tiny file
  (`-l 1`, `-b 100`: 2.2x; `-C`: 7.7x; `-l 1000`: 1.3x). The `-C` figure is the
  per-boundary slow path in `Splitter.splitLineBytes`; wall time is equal because
  these runs are dominated by system calls.
- Binary size is 5.2x GNU's dynamically linked 60 KB, as in core-utils: the floor
  is std's `Io` runtime. ReleaseSmall: `split` 190 KB, `util-unix` (multicall)
  191 KB.
- History: the first version wrote each `-C` record with its own `write(2)`
  (54x cycles, 13.6x wall); a 64 KiB write-behind buffer plus a backwards
  search for the last whole record in the available room fixed that.

Not measured: pipes as input (`-n N` spools them in memory), `--filter`, the
glibc build (musl and glibc were not both tried; see compatibility record).
